## Deferred / known gaps (not 0.1.0 blockers)

- D1: site data dirs are `setu`-owned while apps run as their site
  user — apps that WRITE (Vyasa media uploads) hit EACCES. Needs a
  chown-to-site-user step in install (helper-covered). E2E does not
  cover app writes (hello is read-only).
- D2: update strategy `command` runs as Restart+Health (R15) — the
  agent-side exec detail is still open.
- D3: `PgSessionStore` custom until upstream sqlx-0.9 support (R18).
- D4: DNS-flip SSRF residual (R20); long-poll polling cost (R22).
- D5: dump-file read for phase-2 S3 upload relies on `setu ∈ postgres`
  group + pg_dump's file mode; revisit in phase 2.
- D6: concurrent xed — installer re-run with an UNPARSEABLE existing
  toml fails loudly (by design, operator moves it aside).
- D7: `has_value: true` is unconditional in env GET; offline-at-create
  is `validation` (400) not `agent_unreachable`; `test.sh`/`test-pg.sh`
  two-worktree same-name race (one-heavy-job rule covers it).

## Rev3 WS1 foundations (2026-10-09)

- R48: config key `bind_addr` is dropped, not aliased: `listen`
  (`unix:<abs path>` | `<ip>:<port>`, default `127.0.0.1:7000`) replaces
  it; e2e and docs use `SETU_LISTEN` — pre-release, an alias would be
  dead code — cost if wrong: an old `SETU_BIND_ADDR` is silently ignored
  and the panel binds the default.
- R49: `listen = "unix:…"` parses but `setu serve` refuses it until the
  WS8 listen module (unix socket + `Peer`) lands — keeps WS1 to config —
  cost if wrong: none before the installer (WS10) writes a unix listen.
- R50: `trusted_proxies` default is `["127.0.0.1/32"]`; bare IPs are
  accepted and widened to /32 or /128; the env form is comma-separated
  (`SETU_TRUSTED_PROXIES=10.0.0.0/8,::1`); a bad entry fails config load
  — the plan writes `["127.0.0.1"]`, which is the same set — cost if
  wrong: a config-format tweak.
- R51: sealing derives the cipher key as SHA-256("setu-seal-v1" || key);
  `Sealer::store(value, secret)` picks `seal`/`seal_plain`; `open`
  refuses unprefixed values (`SealError::Unrecognised`). Values sealed
  by the revision 1 code (raw key) no longer open — nothing is released
  — cost if wrong: re-seal on a dev database.
- R52: `args` live in `[run]` (spec §2), not `[run.binary]`; `Run` is a
  struct (`kind`, `workdir`, `args`, optional `binary`/`image`) and
  targets are `[run.binary."<target>"]` tables (inline keys still parse)
  — the spec's Vyasa example must validate verbatim — cost if wrong:
  manifests stored by revision 1 no longer deserialize (none released).
- R53: `app.id` follows the spec regex `[a-z][a-z0-9-]{1,31}`;
  `startup_grace_s` is bounded 1–3600 and is now the `Health` timeout in
  provision, update and restore (was a fixed 90) — the spec gives the
  meaning but no bound — cost if wrong: an app needing > 1 h of grace.
- R54: `postgres_url` resolves secret regardless of the modifier, and
  `value`s and prompt answers with control characters are refused at
  validation/resolution (spec §2 "env values: no control characters")
  — closes the env-file injection path before the WS2 helper — cost if
  wrong: an app that wanted a tab in a value.
- R55: `setu_manifest::merge` re-resolves `from = "postgres_url"` from
  its input; the update job passes the stored URL (the role password is
  minted once at provision). `once` values are never in the merged env,
  but the update keeps them sealed in `sites.env` for reveal, and the
  rollback env file omits them too — cost if wrong: an operator loses
  reveal of a once value after an update.
- R56: site `data_dir` is stored as the fixed agent root
  `/srv/setu/sites/<id>/data`, no longer derived from the control
  plane's `data_dir` (now `/var/lib/setu`, R47), until WS5/WS6 move path
  derivation to the agent by short id — cost if wrong: none; the value
  equals the revision 1 default.
- R57: corpus is exactly plan Task 3's 17 cases; the dropped revision 1
  cases (backup dir undeclared, unknown `from`, dir escape) are unit

- R58: `apps/hello` reads `HELLO_BIND` (falling back to `0.0.0.0:$PORT`)

## Rev3 WS2 privileged helper (2026-10-09)

- R60: `nix` 0.31, not the plan's 0.29: 0.31's `openat`/`Dir::from_fd`
  take and return `OwnedFd`, so the `O_NOFOLLOW` walk needs no `unsafe`
  (the workspace forbids it) — cost if wrong: none (API-compatible
  subset). `renameat2(RENAME_EXCHANGE)` is glibc-only in nix, and the
  release target is musl, so `restore` swaps with two `renameat`s (old
  dir into staging, new dir into `data/`) while the unit is stopped —
  cost if wrong: a crash between the two renames leaves `data/<dir>`
  missing until the restore is re-run (the old copy is still in the
  staging dir).
- R61: stdin framing for every verb is one line of JSON (the input),
  followed by the raw tar.zst for `restore` only; stdout is one line of
  JSON, or the raw tar.zst for `backup`. The spec says "JSON on stdin"
  and "tar on stdin" for `restore` without a framing — cost if wrong: a
  framing change in two places (`helper::cli`, `helper_client`).
- R62: `setu-agent.service` has `ReadWritePaths=/var/lib/setu /etc`, not
  only `/var/lib/setu` (spec §4). sudo children share the unit's mount
  namespace, so under `ProtectSystem=full` the helper could neither
  write the drop-in under `/etc/systemd/system` nor run `useradd`
  (`/etc/passwd` lock files). The revision 1 e2e hit exactly this
  ("cannot lock /etc/passwd"). `/etc` is still not writable by the
  `setu` user (file modes); `full` keeps `/usr`, `/boot` and `/efi`
  read-only. The obsolete `RuntimeDirectory=sudo` was dropped too —
  cost if wrong: if a narrower path set works, WS9's e2e can tighten
  it. Spec question for the owner: change §4's text to match.
- R63: `write-unit` takes the helper-local `UnitInput { short_id,
  version, exec, args, workdir, memory_mb, cpu_percent }`. Until WS5
  adds `workdir` to the proto `SiteSpec`, the agent sends `exec_dir`
  (the manifest default), `exec` relative to `bin/current` (the binary
  ref's, else derived from the spec path), and a version of `"0"` when
  none is known (it is only validated) — cost if wrong: a site with
  `workdir = "bin"|"data"` runs in the exec dir until WS5.
- R64: the env file is written in systemd's `EnvironmentFile=` syntax,
  `NAME="value"` with `\`, `"`, `` ` `` and `$` backslash-escaped. The
  revision 1 renderer used shell quoting (`'…'\''…'`), which systemd
  does not parse. Values with control characters are refused, and the
  error never quotes the value — cost if wrong: none.
- R65: dispatch keeps proto's `Backup { dest }`/`Restore { src }` for now
  but uses only the path's last component as a backup name
  (`[A-Za-z0-9._-]{1,64}`). The agent writes and reads
  `/var/lib/setu/backups/<short>/<name>/{db.dump,dirs.tar.zst}` itself,
  so the control plane cannot steer the location (finding 3, part).
  `restore` takes its dir list from the archive's top-level entries.
  WS5/WS6 replace this with `backup_id` — cost if wrong: none (archives
  are unreleased; the old `files.tar.gz` layout is gone).
- R66: `scripts/check-sudoers.sh` checks the asset against the golden
  text, then runs classic `visudo -cf` on a 0440 copy (`visudo.ws` is
  preferred when present). This host's default `visudo` is sudo-rs
  0.2.13, which rejects `Defaults:setu !requiretty` ("unknown setting");
  classic `visudo.ws` prints "parsed OK" unprivileged, with no
  ownership complaint. The script skips with a message when only
  sudo-rs or no visudo exists. Spec question for the owner: Ubuntu
  ≥ 25.10 defaults to sudo-rs, so either keep 24.04 as the only target
  or drop `!requiretty` (it is the default anyway) — cost if wrong: on a
  sudo-rs host the sudoers drop-in may fail to parse.
- R67: in `--root` mode (feature `test-root`) the CLI uses fake
  users/systemctl and recording ownership. The in-process library API
  (`helper::run` with a `Ctx`) is how the 18 tests run unprivileged. The
  `--root` CLI path itself is covered by re-executing the test binary
  (`zz_helper_child_entry`), with the feature enabled for tests through
  a self dev-dependency. A plain `cargo build -p setu-api` has no
  `--root` (checked: "unexpected argument '--root'") — cost if wrong:
  none.
- R68: postgres calls gained `sudo -n` (finding 9, the hang half), and
  `/srv/setu/sites` is created `root:root 0755` by `agent install`
  (the helper's no-follow walk assumes root-owned parents). The rest of
  `postgres.rs` (password on argv) stays WS4 — cost if wrong: none.
- Known limits left for later sets: `HelperOutput.stdout` buffers a
  whole backup archive in memory (fine for MVP data sizes; WS6 can
  stream to the file). The heartbeat calls helper `unit show`
  (`du -sb`) per site every interval (WS7 owns cadence and caching).
  `install_system` and the WS3 assets (nftables, Caddy) are not in this
  set.

## Rev3 WS3 network and Caddy (2026-10-09)

- R69: `setu-agent.service` drops `ProtectSystem=` and `ReadWritePaths=`
  entirely (supersedes R62). sudo children run in the agent unit's mount
  namespace, so any read-only `/etc` (or `/usr`) breaks the helper's
  drop-in writes and `useradd`; the `setu` user is already kept out of
  `/etc` by file modes. The unit keeps `User=setu`, `Restart=always`,
  `After=network-online.target` and no `NoNewPrivileges`. Spec §4's
  "`ProtectSystem=full` and `ReadWritePaths=/var/lib/setu`" sentence is
  amended in WS12 — cost if wrong: a defence-in-depth layer for the
  agent's own process is absent (the helper never had it).
- R70: `/etc/sudoers.d/setu` drops the `Defaults:setu !requiretty,
  env_reset` line: both are sudo's defaults already, and sudo-rs (the
  default from Ubuntu 25.10) rejects `requiretty` as an unknown setting.
  The file is exactly the helper line and the postgres line;
  `scripts/check-sudoers.sh` no longer skips sudo-rs's `visudo` (checked
  here: both `visudo.ws -cf` and sudo-rs `visudo -cf` print "parsed
  OK"). Spec §4's sudoers block is amended in WS12 (resolves the R66
  owner question) — cost if wrong: none (same effective policy).
- R71: proto `SetRoute`/`RemoveRoute` gain `site_short_id:
  Option<String>` (`#[serde(default)]`), the smallest change that names
  the route `setu-site-<short>`: `state.json` has no domain, so the
  agent could not look the owner up. The jobs set it from the site id;
  the agent **refuses** a route command without it (never derives an id
  from the domain). WS5's proto rewrite may make it required — cost if
  wrong: one field rename.
- R72: `CaddyClient<T: AdminTransport>` holds the admin-API logic once;
  `CaddySocket` = hyper 1 HTTP/1 over `UnixStream` (Host `127.0.0.1`,
  one of the three values Caddy accepts on a unix admin listener, 15 s
  deadline), `FakeCaddy` = the same client over the in-memory
  `FakeAdmin` model (unique `@id`s, `PUT` on an existing id refused,
  `DELETE` of a missing id 404, records requests), so the fake exercises
  the production request sequence. `FakeCaddyServer` (tests/caddy.rs)
  serves `FakeAdmin` with axum on a `UnixListener`. The trait gained
  `routes()` (the merge needs whole route objects; `list_route_ids` is
  derived from it). Verified against real Caddy 2.11.7
  (`caddy:2-alpine`, base config + `caddy validate` for both TLS
  variants): GET 404 → POST, GET 200 → PATCH, DELETE missing → 404 ok,
  `/load` — kept as the opt-in test
  `caddy_socket_against_real_caddy_when_available`
  (`SETU_TEST_CADDY_SOCKET`). `nftables.conf` was loaded twice in an
  `alpine` container next to a foreign table: idempotent, foreign table
  untouched — cost if wrong: none.
- R73: `install_system` always ends with `POST /load` of the base merged
  with the running routes (running routes whose `@id` the base does not
  define, in order, then the base's own: a new panel route replaces the
  old one; without `--panel-host` an existing `setu-panel` is kept).
  When the socket does not answer it first restarts `caddy-api` and
  waits up to 15 s; before that it moves a **foreign** autosave
  (`/var/lib/caddy/.config/caddy/autosave.json` whose `admin.listen` is
  not our socket, i.e. written by the distro `caddy.service`) to
  `autosave.json.setu-foreign`, because `--resume` would otherwise boot
  the Caddyfile config with TCP 2019 open; our own autosave (site
  routes) is kept. `setu-nftables.service` is `After=nftables.service`
  (Ubuntu's `/etc/nftables.conf` starts with `flush ruleset`) and
  `Before=network-pre.target`; it is enabled and **restarted** so a
  re-run reloads the table. `install_system` also writes
  `setu-agent.service` (spec §5's list); `agent install` enables and
  starts it after the join. It is exposed as `setu agent
  install-system [--caddy-only] [--tls internal] [--panel-host H
  --upstream U]` (root; not under `helper`, so not reachable through
  sudo); `InstallSystemOpts.root` is refused unless built with
  `test-root` — cost if wrong: none.
- R74: `agent install` order is apt → user → dirs → Postgres revoke →
  `install_system` → join → start. apt follows Caddy's documented steps
  in one function (`apt_commands`; `debian-keyring` needs Ubuntu's
  `universe`, enabled on stock images; `gpg --dearmor --yes` for
  re-runs). `/etc/setu` is now `root:root 0755` (it was `setu`-owned,
  which let the agent replace `nftables.conf` that root loads);
  `/var/lib/setu` and `downloads` 0750; `backups` stays `setu:postgres
