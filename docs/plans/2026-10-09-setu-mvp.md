# Setu MVP (0.1.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Start with `docs/HANDOFF.md` (repo bootstrap, agents, skills, constraints).

**Goal:** A control plane (`setu`) and a server agent (`setu-agent`) that, on one Ubuntu 24.04 server, provision a single-binary app from a manifest as a limited systemd unit with its own Postgres database and Caddy route, back it up, update it with rollback, and delete it, driven from a React UI, with a real end-to-end test.

**Architecture:** One Cargo workspace, crates `common` (config, sealing, ids), `manifest` (pure validator + env resolution), `proto` (agent command/result types), `db` (sqlx repos + migrations), `jobs` (state machines over an `AgentClient` trait), `api` (axum, utoipa, embedded UI, `setu` binary), `agent` (`Runtime` trait, `NativeRuntime`, systemd/Postgres/Caddy adapters, `setu-agent` binary), `testkit` (throwaway Postgres, test server), `apps/hello` (tiny Axum app used by tests). Control plane talks to agents only through long-polled commands; every command is idempotent.

**Tech Stack:** Rust stable (axum 0.8, sqlx 0.9 postgres+runtime-tokio, tokio, utoipa 5, tower-sessions, argon2, chacha20poly1305, reqwest rustls, clap 4, zbus 5 optional, rust-embed), Vite + React 19 + TypeScript + TanStack Router/Query/Table + Tailwind 4 + shadcn/ui + vitest, pnpm, Docker for test Postgres and the e2e systemd container.

**Spec:** `/home/gopal/Desktop/wp/setu/docs/specs/2026-10-09-setu-design.md`

## Global Constraints

- Repo: `/home/gopal/Desktop/wp/setu`, remote `origin` = github.com/vyasa-cms/setu (private; never make it public without the owner). Work on feature branches in worktrees `../setu-work-<n>`; squash-merge to `main` locally; PRs against `origin/main`.
- No Claude co-author trailers or "Generated with Claude Code" lines in commits or PRs (owner rule).
- Never touch the host's production Postgres on port 5432 nor any `vyasa` database. Test Postgres is a throwaway container on `VYASA_TEST_PG_PORT`-style env `SETU_TEST_PG_PORT` (default 55440). Check `df -h /` before long builds; `CARGO_BUILD_JOBS=4`, one heavy cargo job at a time.
- Never `pkill` by name (production `vyasa serve` runs as this user). Stop scratch processes only by saved PID.
- Absolute paths in every shell command (parallel Bash calls share one cwd). Scratch files in the session scratchpad, not `/tmp`.
- Control plane defaults: bind `127.0.0.1:7000`; `SETU_DATABASE_URL` required; `SETU_SECRET_KEY` required (64 hex chars) — boot refuses otherwise with a one-line message; `SETU_PUBLIC_URL` required for agent join commands.
- Agent defaults: `/var/lib/setu/state.json`, sites at `/srv/setu/sites/<id>`, ports 20000–29999, Caddy admin `http://127.0.0.1:2019`, Postgres admin via peer auth as `postgres` through `sudo -u postgres psql` in phase 1 (the `tokio-postgres` path is a Ruling if an executor finds peer auth unavailable).
- Unit name `setu-site@<site-id>.service`; site user `setu-site-<id>`; env file `/srv/setu/sites/<id>/env` mode 0600.
- IDs: ULIDs as `String` in Rust and `text` in Postgres (`ulid` crate). Site short id = last 8 chars lowercase, used in db names `site_<short>` and user names.
- Secrets sealed as `v1:<base64 nonce||ciphertext>`; plain values never carry a prefix. Logs never print env values; `StorageInput`-style manual `Debug` on every struct holding secrets.
- API: `/api/v1`, JSON, errors `{ "error": { "code": "...", "message": "..." } }` with codes `validation`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `agent_unreachable`, `internal`. 400/401/403/404/409/502/500 respectively.
- UI: same eslint/prettier/tsconfig as Vyasa's `admin/`; `pnpm gen:api` reads `openapi.json` from the repo, never a running server.
- Every task ends green: `cargo fmt --check && cargo clippy --workspace --all-targets -- -D warnings && scripts/test.sh` (Task 1 creates `scripts/test.sh`), plus `pnpm -C ui lint && pnpm -C ui typecheck && pnpm -C ui test` for UI tasks.

## Review Focus

1. A manifest whose `env` references a dir not listed in `needs.dirs` — must be a validation error naming both keys — Task 3 corpus case `env_dir_not_declared.toml`.
2. Two provision jobs for the same server racing on port assignment — must never hand out the same port — Task 7 test `ports_are_unique_under_concurrent_provisioning`.
3. Agent restarts mid-provision (command delivered, result never posted) — the control plane must time out the command (120 s), re-queue it, and the agent's idempotent handling must make the retry succeed — Task 8 test `redelivered_command_is_idempotent` and Task 11 e2e step "kill agent during provision".
4. A health check that passes then the app crashes before the route is set — the site must end `failed`, not `running`, and the route must not exist — Task 9 test `crash_after_health_before_route_is_failed`.
5. An update to a binary whose checksum mismatches — must fail before stopping the old site (no downtime), status stays `running` with the old version — Task 9 test `bad_checksum_update_never_stops_the_site`.
